`apps/web/src/lib/step-view.ts` 的 `hitRate` **只取最后一次模型调用**，
不要改为整轮累计。用户已确定这一口径，并为此纠正过一次
（2026-08-20，曾以「同一行其余四格都是累计」作为理由改成累计，被用户当场否定）。

**Why:** 这一格回答的是「现在缓存生效了吗」，不是「这一轮平均命中多少」。
一轮中第一次调用必然未命中，累计口径把它计入平均，长轮次的命中率被拉低，
该数值就无法回答用户实际关心的问题。它随「这一轮追加了多少新内容」上下波动
是正常现象，不是缺陷：追加一万四千 token 的工具结果时，新增部分本来就不可能命中。

**How to apply:** 该数值忽高忽低时不要变更口径。可以调整的只有取值细节：
最后一次未回报缓存字段时按 0 计算（计费侧 `computeCost` 的 `cachedTokens ?? 0`
也按此计算），只有该次连 usage 都未返回时才显示「未回报」。
逐轮的数值在运行详情面板中按 `provider_requests` 原样列出，那是数据库中的原始记录，不要修改。

同类判断参考 [[diagnose-from-the-local-db]]：命中率降到 0 时先查看相邻两次请求的
`sent_at` 间隔：超过 5 分钟即为缓存 TTL 过期（xhigh 下一次思考耗时 17 分钟，必然过期），
再检查前缀指纹是否稳定，最后才考虑端点在多个上游之间轮询。
