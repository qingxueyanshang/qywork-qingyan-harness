`apps/web/src/lib/step-view.ts` 的 `hitRate` **只看最后一次模型调用**，
不要改成整轮累计。用户已经定过这条口径，并且为此纠正过一次
（2026-08-20，我拿「同一行其余四格都是累计」当理由改成了累计，被当场推翻）。

**Why:** 这一格回答的是「现在缓存生效了吗」，不是「这一轮平均命中多少」。
一轮里第一次调用必然未命中，累计口径把它摊进去，长轮次的率被压低，
那个数就回答不了用户真正在问的问题。它随「这一轮追加了多少新内容」上下起落
是正常的，不是缺陷——追加一万四千 token 的工具结果，新增部分本来就不可能命中。

**How to apply:** 看到这个数字忽高忽低不要动口径。可以动的只有取值细节：
最后一次没回报缓存字段时按 0 算（计费侧 `computeCost` 的 `cachedTokens ?? 0`
就是这么算的），只有那一次连 usage 都没回来才显示「未回报」。
逐轮的数在运行详情面板按 `provider_requests` 原样列，那份是数据库里的原始记录，别动。

同类判断参考 [[diagnose-from-the-ledger]]：命中率忽高忽低多半是端点在多个上游
之间轮询，先去数据库里看前缀指纹稳不稳，再考虑是不是本仓的问题。
