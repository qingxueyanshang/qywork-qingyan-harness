# 权限与沙箱

qywork 只有**两种权限模式**，没有逐次审批弹窗。模式按会话保存，在输入区的「自动审批 / 完全访问」开关上切换，
只影响当前会话；子 agent 按其顶层会话的模式运行。
在「设置 → 通用 → 偏好 → 新对话默认权限」中选择新对话的初始模式，修改后立即保存，只影响之后创建的对话。
该选项对应配置文件中的 `mode`：

```json
{ "mode": "auto", "permissionDefaultsVersion": 1 }
```

旧版输入区开关曾修改全局权限。升级后的首次配置加载会将未迁移的新对话默认值设为「自动审批」，
已有对话保留各自的权限。迁移标记随下一次配置保存一并落盘；此后显式选择的默认权限会在重启和升级后保留。

| 模式 | 行为 |
|---|---|
| `auto`（默认） | 不弹窗。文件工具锁在工作区内，`run_command` 过一张拒绝清单 |
| `full` | 不裁决。权限闸、路径边界、受保护目录一起不设 |

逐层对照——**两种模式的差别只有前四行**：

| 这一层 | `auto` | `full` |
|---|---|---|
| 文件工具（read / write / edit / glob / grep / list_dir）的路径 | 锁在工作区 + `additionalDirectories`，越界拒 | 不设，任何绝对路径都解析得到 |
| 文件工具写 `.qy/` | 拒 | 不拒 |
| `run_command` 的命令串，以及模型写入、启用、迁移 MCP 服务时的启动命令 | 过拒绝清单，命中即拒 | 不裁决，直接放行 |
| `run_command` 的 `cwd` 参数 | 与文件工具同一份根目录清单，越界拒 | 不设 |
| 内核沙箱（只有 Linux / WSL2 / macOS 有） | 工作区 + `additionalDirectories` 可写，其余只读，凭证目录读不到 | 一样生效：沙箱那一层不看权限模式 |
| 凭证剥离与输出脱敏 | 生效 | 生效 |
| `web_fetch` 的 SSRF 闸、`run_command` 的 `probe_url` 只准回环 | 生效 | 生效 |
| shell 出网 | 默认不限，`sandboxNetwork: "deny"` 只在有内核沙箱的平台上生效 | 同左 |
| 界面与 HTTP 触发的配置写入 | 与权限模式无关，各自的守卫见下 | 同左 |
| 项目 `.agents/mcp.json` 中的服务 | 用户确认过当前内容后才启动，见下 | 同左 |

---

## 为什么没有「每次问一下」

弹窗的问题不是麻烦，是**粒度骗人**。

你看到 `npm test` 点了批准，实际批准的是「任意本机操作 + 全部环境变量」——
`run_command` 是唯一一条能同时绕开路径约束和 SSRF 校验的路径，
因为命令字符串里的路径不经过 qywork 的参数解析。

而弹窗一多，人就会去打开「全部自动批准」。防线不是被攻破的，是被自己关掉的。
与其如此，不如把两端做清楚：要么有一套确定的裁决，要么明说不裁决。

**`auto` 下被拒不是弹窗**，是把拒绝理由作为工具失败结果交回给模型，
让它换个做法（「写不了工作区外的路径」→ 它会改成写工作区内）。你不会被打断。

## 内核沙箱（有就有，没有就没有）

`auto` 的裁决全是**文本判断**：拒绝清单是一张想得到才写得出的表。
它挡不住一个没想到的写法，而「没想到」按定义列不完。

内核层不一样——它不看命令长什么样，只看系统调用打到哪个 inode。

| 平台 | 后端 | 有没有 |
|---|---|---|
| Linux / **WSL2** | bubblewrap | ✅ 装了 `bwrap` 就自动启用 |
| macOS | seatbelt（`sandbox-exec`） | ✅ 系统自带，自动启用 |
| **原生 Windows** | — | ❌ 还没接 |
| WSL1 | — | ❌ 没有独立内核，namespace 不可用 |

```bash
qy doctor     # 一屏看完：配置、沙箱、账本、MCP、插件
qy config     # 只看配置与沙箱那两条
```

桌面端和手机端也看得到：沙箱状态在握手能力里，侧栏底部有一条常驻的
「✓ 沙箱 bwrap」或「⚠ 无内核沙箱」，悬停能看到完整理由。
**没有沙箱时反而更要显示**——那是很多机器上的默认状态，它不会主动报错。

**这几档不合并成一个「有沙箱」的布尔值。** 把「开」读成「全都保住了」，
是这套模型最危险的误解。

**「装了」不等于「能用」，所以启动时会真跑一次。** Ubuntu 24.04+ 默认禁掉
无特权用户命名空间，那种机器上 `bwrap` 在 PATH 里但一条命令都起不来。
`qy config` 报的是**实测结果**，不是「查到了这个二进制」——跑不起来会连同
原因和修法一起告诉你（通常是一句 `sysctl -w kernel.apparmor_restrict_unprivileged_userns=0`）。

沙箱开着时的边界：

| | |
|---|---|
| 工作区 + `additionalDirectories` | 可读**可写** |
| 其余整个文件系统 | 可读、**不可写** |
| `~/.ssh`、`~/.aws`、`~/.gnupg`、`~/.docker`、`~/.kube`、`~/.config/gh`、`~/.config/gcloud`、`~/.qywork` | **读不到**（bubblewrap 挂成空目录，seatbelt 直接拒绝读） |
| `.qy/` | 可读、不可写（在可写根之上再盖一层只读） |
| 宿主进程表 | bubblewrap：看不见（独立 PID namespace + 新挂的 `/proc`）。seatbelt 无此项 |
| 网络 | 默认**不受限**，可整个断掉，见下 |

两个后端形状完全不同（一个是挂载表，一个是规则集），但**承诺的是同一句话**——
有一组测试专门钉这一点，免得两边慢慢分叉成两套语义。

**这是写边界，不是读边界。** 工作区外的普通文件仍然读得到——
要做读边界就得只挂载少数几个目录，而那样 `/usr`、`/lib`、`/etc` 全没了，
基本什么都跑不起来。所以凭证目录是**单独点名盖掉**的，那是一份列举，
和拒绝清单一样有「没想到就是个洞」的性质。

**网络默认不受限，但可以整个断掉。**

```json
{ "sandboxNetwork": "deny" }
```

只有两档，**刻意不做域名白名单**：中间态要在沙箱里起代理、沙箱外做转发、
还要让 TLS 校验认一张自签 CA，那套组件坏起来的表现是「网络时好时坏」，
比没有这个功能糟得多。

默认是 `allow`，因为断网的 agent 装不了依赖、拉不了代码，而报错跟网络毫不相干
（包管理器只会说拉取失败）——查到原因之前你会先把整个沙箱关掉。

`deny` **只在有内核沙箱的平台上生效**，配了而本机没有沙箱时启动会明说它没生效。
保持默认时，shell 命令的出网**没有边界**——`web_fetch` 那条路有 SSRF 闸，
shell 这条没有。

## 裁决

`auto` 下有两处判定：**文件工具的路径**（确定性判断，越界的走不到裁决层），
以及 **`run_command` 的一张拒绝清单**。`full` 下这两处都不设。

另有一层与模式无关：**凭证剥离**。它防的不是越权，是凭证泄漏，
所以「完全访问」也不豁免它。

### 凭证剥离（两种模式都生效）

| 做什么 | 为什么 |
|---|---|
| 凭证不进子进程 | 模型自己编的命令继承整份环境 = 一句提示注入就能 `env \| curl` |
| 输出里的凭证明文屏蔽掉 | 只堵输入侧的话，`cat .env` 照样把 key 送进上下文再发给供应商 |

判据有两条，**按值那条最硬**：

1. **值命中**——配置里所有档案的 key 明文。不管环境变量叫什么名字都能抓到，
   白名单也豁免不了它。太短的值（少于 8 个字符）不参与按值匹配：
   一个写成 `"1"` 的 key 会让整份环境全部命中，而命令失败时没有任何指向脱敏的线索。
2. **名字像凭证**——`*_KEY` / `*_TOKEN` / `*_SECRET` 之类。误伤率最高，所以有白名单出口。

```json
{ "envAllowList": ["GITHUB_TOKEN"] }
```

`SSH_AUTH_SOCK` 默认放行：剥掉它 `git push` 直接失败，而它是个**套接字路径**
不是可外泄的明文——打印出来发给别人没有用处。

### 禁止写「会给自己加工具」的文件（只在 `auto`）

它由 `resolveWritablePath` 实现（`isProtectedPath` → `ProtectedPathError`），
**只作用于走那个解析器的写入**——`run_command` 里的路径不经过它。

工作区里的 agent 配置按「能不能改变模型的能力」分成两类：

| 路径 | agent 能不能写 | 为什么 |
|---|---|---|
| `.agents/mcp.json` | **能** | 其中的服务经用户确认后才启动（见「项目 MCP 服务的启动确认」），新写入的内容回到待确认，路径层不再拦截 |
| `.qy/team.json` | `write_file` **不能**；`define_role` 能 | 整份改写会连同 `rules.shared`（用户对这台机器定的纪律）一起冲掉，所以只留一条读出原文、只替换 `roles` 里那一项、其余键原样写回的路径 |
| `.agents/memory/*.md` | **能** | 记忆是 agent 自己的笔记本，不改变它的能力边界。约定的写法是 `write_memory` / `delete_memory`（各自要过权限闸），但路径层不强制这一条 |
| `.agents/skills/<name>/` | **能** | 一篇 SKILL.md 是一段提示词，不给新能力。挡了它，设置页那颗「新增技能」就等于点了没反应 |

所以准确的说法不是「禁止写配置目录」，而是**禁止写那些会改变自身能力的文件**。

**`full` 下这一层不设。** 该模式下 `run_command` 全部放行，一行重定向即可写入；只拦截文件工具的结果
不是更安全，而是「文件工具拦截、shell 不拦截」的两套账。有内核沙箱的平台上仍有一层：`.qy/` 在沙箱中
是只读挂载，而沙箱不区分权限模式。

### 项目 MCP 服务的启动确认（与模式无关）

项目的 `.agents/mcp.json` 位于仓库内，其内容可能来自仓库作者或一次 `git pull`。其中的服务只有在用户
确认过**当前内容**后才启动；内容被修改后回到未启用。确认记录保存在 `~/.qywork/mcp-approvals.json`，
不写入仓库。

- 未启用的服务不在任何时机启动（服务启动、打开设置页、发出消息），设置页在「未连接」中显示其命令与
  「未启用」。
- 模型从每轮的运行快照中得知这些服务及其命令，向用户列出命令并取得同意后，调用 `enable_mcp_server`
  启用。`auto` 下该调用与 `run_command` 经同一张拒绝清单判定。
- 经 qywork 写入项目层的服务（设置页新增与导入、`write_mcp_server`、`move_mcp_server`）在写入时即确认。
- 全局的 `~/.qywork/mcp.json` 只能由用户或经 qywork 写入，不需要确认。

「先询问再启用」由工具说明约束，系统不强制；系统强制的是命令判定，这与 `auto` 下 `run_command`
相同：模型执行命令前同样不逐条征求同意。

### 用户经界面的写入不在这条边界内

服务端有几条由**用户动作**触发的配置写入路径，各有守卫，都与权限模式无关：

| 路径 | 触发者 | 守卫 |
|---|---|---|
| `~/.qywork/config.json` | 设置页保存 | 落盘前跑一遍配置体检，有致命问题回 422 且一个字节都不写 |
| `.qy/team.json` | 编辑器面板保存 | 落盘前 `JSON.parse`，坏 JSON 回 422 |
| `.agents/memory/*.md`、`~/.qywork/memory/*.md` | 记忆面板增删 | key 安全化 + 再过一遍工作区边界；空、超长、超条数上限都回 422 |
| `~/.qywork/attachments/<会话 id>/*` | 粘贴 / 拖入 / `+` 号上传 | 会话 id 里的分隔符与 `..` 一律拒；文件名安全化后落进该会话自己的目录 |

判据是**谁按下的**：这些是你在改自己的文件，不是模型在给自己提权。

附件那条**没有自己的体积上限**，兜住它的是 HTTP 入口那条 1 GB 的请求体上限——
那是「别让一个已配对的客户端用无界请求塞满磁盘」的安全线，不是模型能收多大的媒体。
具体模型更小的限制由 Provider 在请求时裁决，两者不是一回事。

### `run_command` 的拒绝清单（只在 `auto`）

文件工具（read/write/edit/glob/grep）的路径已经被锁死在工作区内，越界的根本走不到
裁决层，所以它们直接放行；调用 MCP 工具与插件工具同样放行：它们是用户配置或安装的。
需要裁决的是声明了命令行的调用：`run_command`，以及写入、启用、迁移 stdio MCP 服务的
`write_mcp_server`、`enable_mcp_server`、`move_mcp_server`（写入即启动其命令）。命令字符串中的路径不经过参数解析。
Linux / macOS 上 MCP 进程不经过内核沙箱，`run_command` 经过；这一差异尚未处理。

**只有拒绝清单，没有允许清单，也没有「判不了」这一档。** 它只回答一个问题：
这条命令会不会造成「不可逆且越出工作区」的后果。判不出它属于下面三类就说明它不属于，
放行——包括工作区内的任何读写与执行、**读**工作区外的文件、起本地服务器、装包、`git push`。

1. **往工作区之外写或删。** 家目录与系统目录，**符号写法和字面绝对路径都认**：
   `~/`、`$HOME`、`%USERPROFILE%`、`$env:APPDATA`、`$PROFILE`、`C:\Users\你\…`、
   `/etc`、`C:\Windows`、盘符根。读不拦——读不改变状态，而「把凭证读进上下文」由第 3 条管。
   这是三条里**唯一**能被 `additionalDirectories` 放开的：它判的是位置，
   而位置正是额外目录要改的那一维。
2. **改系统状态。** 提权（`sudo` / `runas` / `-Verb RunAs`）、关机重启、递归删根目录
   或家目录、格式化与写裸设备、fork 炸弹。
3. **碰凭证文件，读也算。** SSH 私钥、`.aws/credentials`、`.config/gcloud/`、
   `.kube/config`、`.npmrc`、`.netrc`、`.pgpass`、`.docker/config.json`，
   以及 qywork 自己的 `~/.qywork/config.json`。读出来就进上下文、随下一次请求发给
   供应商，**发出去就收不回**。

**每条规则要么锚在命令位**（`;` `&&` `|` `{` 换行之后的每一段）**，要么扫整个命令串**，
所以 `ls && rm -rf ~` 里的第二段照样被抓到，不需要先判「这是不是单条命令」。

**POSIX 与 PowerShell 两种写法都认，而且不看 `process.platform`**：外层 shell 是哪个
由本机装了什么定，而一条命令完全可能在一台机器上被裁决、在另一台上被执行。

**「下载即执行」有意不在表里。** 盯 `curl … | sh` 拦的是一种写法而不是这件事——
分两步写就绕过，`npm install` 任意包的安装脚本同样在跑第三方代码；而误伤是实打实的：
rustup、bun、deno、homebrew 的官方安装方式**就是** `curl … | sh`。
拦不住想拦的、又误伤真实用法，就不该留着假装有一道防线。

## 让 agent 碰工作区之外

```json
{ "additionalDirectories": ["/Users/me/notes", "D:\\datasets"] }
```

只接受**绝对路径**——相对路径的基准是启动 `qy` 时所在的目录，换个地方启动含义就变。
配错的条目会在启动时被指出来，不会静默失效。

这个清单**同时接进三层**：路径解析、拒绝清单、沙箱的 bind 列表。
三层里漏掉任何一层，症状都是「配了但不管用」，而各自的错误信息完全不同。

它**主动放宽边界**，所以有两条要看清楚：

- 加了 `~/notes` 只放开那个目录，**不是**给家目录发通行证——`cat ~/.ssh/id_rsa` 照样拒。
- `full` 下这个清单没有意义：那个模式里路径边界整个不设，配不配都一样。
  它是 `auto` 的机制。`.qy/` 的保护同样只在 `auto` 下成立。

## 已知边界，如实写

- **没有内核沙箱的平台上（原生 Windows、WSL1），`run_command` 只剩文本规则。**
  拒绝清单是正则匹配，不是内核沙箱：它读命令串，不看系统调用打到哪个 inode。
  路径约束管的是工具**参数**，管不了命令字符串里的路径。规则钉死的是家目录与
  系统目录（**符号写法和字面绝对路径都认**：`~/`、`$HOME`、`%USERPROFILE%`、
  `C:\Users\你\...`、`/etc`）、提权、毁盘、写 SSH 凭据。
  **规则封不住的那一类**是：工作区外**且**家目录外的路径（另一块盘、
  `C:\ProgramData`、网络共享）。想要那一层也有边界，目前的办法是
  **在 WSL2 里跑 `qy`**。
- **有沙箱的平台上，边界是「写」不是「读」。** 工作区外的普通文件仍然读得到，
  只有点名的那几个凭证目录不可见。那份名单是列举，会漏。
- **shell 命令的出网默认完全不受限**（`sandboxNetwork: "deny"` 可以整个断掉，
  但没有中间档）。
- **macOS 那一档由运行期自检保证，不是由 CI 保证。** 本项目的开发机不是 Mac，
  seatbelt 的 profile 只有纯函数测试；真正确认它可用的是启动时那次实跑，
  失败会降级报「没有沙箱」。
- **剥了环境变量不等于命令读不到 `.env`。** 这是收窄不是墙（`.env` 在工作区里，
  沙箱开着也一样读得到——它本来就该读得到）。
- **写 `.qy/` 只有两层**：文件工具是确定性拦截（`resolveWritablePath`，只在 `auto`），
  沙箱是内核只读挂载。原生 Windows 上只剩第一层，shell 那侧写得进去；`full` 下
  第一层也不设。拒绝清单**有意不收这一条**（`agent/src/policy.ts`）：模型手里已经有
  `run_command`，自己加个工具并没有获得新能力，而拦了 shell 不拦工具就是同一件事两套账。
- **`full` 下，有内核沙箱的平台上两侧不同宽。** 文件工具跑在 qy 自己的进程里，
  路径边界一撤就写得到任何位置；而 shell 起的是子进程，仍被 bubblewrap / seatbelt
  按「工作区可写、其余只读」挂着。于是同一个模式下 `write_file /etc/x` 写得进去、
  `echo > /etc/x` 被内核拒。原生 Windows 上没有那一层，两侧一致。

## 旧配置

`autoApprove` 已经不再生效。**不会**自动映射成 `full`——
那等于在你没表态的情况下把防线拆掉。它一律按默认的 `auto` 运行，
并且每次启动都会提示一次，直到你把那行删掉。
