## 一、需求与边界

1. 多个模型会在工具轮之间反复写“收到提示”“继续第 N 步”“确认清楚了”“记忆已写入”等开头；
   不是只有 Qwen，也不是只有 todo。
2. 正常正文、真正发生变化时的执行进度、用户主动询问的状态都必须继续输出。
3. 不按模型逐个加禁词，不新增正文过滤器，不在 UI 隐藏内容。
4. 不改变提示词规则和注记文案；修复消息装配、回放与压缩结构。
5. 保持同一 run 内、跨 run、压缩后和进程重启后的模型可见历史同形，不牺牲缓存换取表面安静。
6. 自动化只能证明请求结构；还要用真实端点验证模型行为和 provider 回报的缓存数据。
7. 真实验收必须在 qywork 里产生用户可打开的工作区与对话，形状参照现有“子agent演示”，
   不能用 fake provider、单测输出或一次 CLI 问答冒充真实对话。
8. 正常执行结束后，前端收尾条不新增也不保留“已完成”文字；耗时、token、命中率、金额照常显示，
   异常停止原因照常显示。模型最终正文可以自然总结完成情况，不做正文过滤。

明确不做：

- 不新增“不要说收到/继续/确认”的提示词。
- 不用正则删除模型正文，不拦截“第 N 步”等正常内容。
- 不加 Qwen、GLM、DeepSeek、Claude 的单模型行为分支。
- 不把动态注记重新塞进冻结 system 前缀。
- 不把旧的 `tailNotes → system → user <system-reminder>` 留作兼容兜底。
- 不把内部上下文写进 `messages.content`，避免 UI、导出和用户原文被污染。
- 不用“正常结束显示已完成”作为本修复的完成反馈；成功态保持原来的静默投影。

## 三、A2 五问

1. **当前唯一权威**：用户原文以 `messages` 为权威，执行事实以 `runs/steps` 为权威，
   `runtime/transcript.ts::buildHistory()` 把两者投影成模型历史；`AgentLoop.buildRequest()` 负责本 run 的追加；
   provider 适配器只负责协议序列化，不应重新解释消息身份。
2. **最早错误点**：共同错误最早出现在 `AgentLoop.buildRequest()`——它把内部上下文当成每次 provider
   请求都新产生的 conversational message。Chat/Anthropic 适配器随后把它进一步伪装成 user，
   所以工具结果之后总有一个“新用户”催模型确认；Responses 虽保留 system 角色，也仍重复产生新指令。
3. **原地改点**：把 `buildTailNotes()` 的求值从“每次 provider 请求”上移到现有 `Session.ask()` 的 run
   边界，冻结为该 run 的输入快照；快照随既有 run 行落库，并由既有 `buildHistory()` 绑定到该 run
   对应的真实用户消息。run 内变化继续通过真实工具结果表达；压缩只复用已落库的最新 run 快照并保留
   最后一次成功 `write_todos` 的真实调用/结果，不重新计算、不再持久化第二份 context/todo。
4. **删除清单**：删除 `LoopDeps.tailNotes`、`AgentLoop.buildRequest()` 的 notes 追加与尾注断点逻辑、
   三个适配器对 conversational system 的特殊分支、`WireMessage.role='system'`、保护旧 user-reminder
   形状的测试和过时注释。保留 `buildTailNotes()` 的全部模型可见字符串。
5. **路径增减**：**否，不增加。**
   - 真源数：不变，仍是 messages/runs/steps；`runs.context_snapshot` 是 run 输入信封的一列，不是能独立裁决行为的新账。
   - 状态账数：不变；`conversations.compaction_manifest` 不新增 context/todo 副本，todo 仍只认最后一次成功 step。
   - 执行入口数：不变，仍从 `Session.ask()` 进入同一个 `AgentLoop`。
   - 持久化路径数：不变；run 初始 INSERT 只多一个内部输入信封列，没有新表、manifest 字段、后台流或补偿任务。
   - provider 可见的伪 user 数：减少为 0；真实 user 与 Anthropic 协议规定的 tool_result user 保留。

A2 准入通过，可在用户确认后实施。

### 3.1 前端“已完成”投影的独立 A2 校验

1. **当前唯一权威**：run 的真实终态仍在 `runs.stop_reason`；会话流只由 `RunStatusBar` 投影，
   运行详情由 `runMark()` 投影。隐藏正常 completed 不改变账本。
2. **最早错误点**：`dfce073` 把 `Transcript.tsx:587` 的条件放宽为“任何 stopReason 都显示”，
   同时新增测试要求“已完成”；不是 Agent Loop 的终态判断本身。
3. **原地改点**：恢复成功态静默——只有错误正文或非 completed 的异常停止原因进入 `.run-reason`；
   耗时、usage、命中、金额与星河条的完成视觉不动。
4. **删除清单**：删除“停止原因永远显示、正常完成也显示”的注释与“正常完成显示已完成”测试；
   不撤销 `dfce073` 中“未完成 todo 不得误判 completed”的循环修复。
5. **路径增减**：**否。** 不新增状态、事件、组件或持久化；仅恢复既有 UI 投影条件。

## 四、方案节

### 4.1 唯一数据流

```text
run 开始
  └─ Session 刷新扩展 / 技能 / 记忆索引
      └─ buildTailNotes()（模型可见文案原样，求值一次）
          └─ createRun(... context_snapshot)（同一条 run INSERT）
              └─ buildHistory()
                  └─ context + 图片 + 用户原文（同一条真实 user，用户原文最后）
                      └─ AgentLoop：history + 只追加 transcript
                          └─ provider adapter：只序列化，不再 system→user
```

压缩发生时：

```text
既有 compaction_manifest 只推进摘要线 / 收纳线
  ├─ 复用 runs.context_snapshot 中最新一份已落库输入信封
  ├─ 保留最后一次成功 write_todos 的真实 assistant tool_call + tool_result 单元
  └─ 不调用 buildTailNotes()，不新增 context/todo manifest 字段，不修改 messages.content
```

### 4.2 消息承载规则

- 账本/AgentLoop 内部使用专用的非对话 context 段保留分组；三个适配器必须在协议序列化前把同一 run 的
  context 与真实 user 合成一个 provider user 条目，不能把 context 单独发成 user/system。
- 文本用户消息：provider 最终条目中内部 context 在前，用户原文逐字放最后；不再生成 `<system-reminder>` 包装。
- 带图消息：provider 最终条目中 context 文本块在前，图片块保持原顺序，用户文字仍是最后一个文本块。
- `messages.content`、前端事件和归档中的用户正文保持原值；内部 context 只存在于 run 输入快照和模型投影。
- 每个 run 的快照冻结：自动重发、断流重试、每个工具 step 都复用同一字节，不重新扫描、不回写早期消息。
- 下一条真实用户消息创建下一 run，并在历史尾部追加新的“用户原文 + 当时 context”；因此上一 run 的完整
  provider 字节是下一 run 的前缀，不把上一轮工具结果挤出缓存。
- 存量 run 的 `context_snapshot=NULL` 不猜、不回填。升级后的第一条请求允许一次请求形状变化；之后按新结构稳定。

### 4.3 为什么不按模型特调

根因发生在 provider 之前。按 Qwen/GLM/DeepSeek/Claude 分别加规则会保留同一个错误生产点，
还会让换协议、中转站改模型名时重新漏出。模型库只描述能力、价格、窗口和协议差异；
“内部上下文是不是用户说的”是 harness 的统一语义，不能进模型映射库。

### 4.4 真实成本与边界

- **数据库**：每个新 run 多存一份 context JSON。典型空索引约几十 token；技能/记忆/MCP 很多时可到千级。
- **上下文**：快照会随未压缩的真实用户轮累计；代价换来跨 run 字节只追加。压缩后旧快照随旧用户轮进入
  既有摘要，只保留最新已落库快照，不在 manifest 再复制一份。
- **性能**：不新增扫描；现有每 run 的技能/记忆/扩展刷新提前到 run INSERT 前完成，以便快照原子写入。
  第一条 `run.started` 事件可能稍晚，但首个 provider 请求总耗时不应增加；批 5 要实测首次事件和首 token。
- **安装包**：只有 TS 与一条 SQLite 迁移，项目体积增量可忽略；不引入依赖、浏览器内核或运行服务。
- **缓存**：发布后旧会话第一次请求因线形变化预期有一次冷启动；新线形稳定后，同 run 与跨 run 均只追加。
- **模型行为**：结构性消除“工具结果后又出现新用户提示”，但不承诺模型永不使用“继续”二字；用户真的要求
  状态、或进度确实更新时，模型仍可正常说明。

## 五、对抗复审

被推翻的方案：

1. **再改提示词，扩展禁词列表——毙掉。** 现有文案已经禁止重复播报，账本仍有跨模型样本；
   再写“不要说收到/继续/确认”会误伤正常正文，且没有消除新 user 消息。
2. **前端隐藏重复开头——毙掉。** 模型的后续推理仍基于错误历史，缓存与 token 一分不少，用户也无法看到
   真正正文是否被连带删掉。
3. **适配器直接把尾注改回 system——毙掉。** DeepSeek 模板会把动态 system 收拢到冻结前缀后，
   `openai-compat.ts:475-482` 已记录真实缓存断崖。
4. **只在内存冻结一次，不落库——毙掉。** 重启后 `buildHistory()` 无法重建上一 run 的相同字节，
   provider 前缀从旧用户消息处断裂；历史和活 transcript 也会不同形。
5. **每个 provider 请求重写当前用户消息中的 context——毙掉。** 虽然没有新增 user 轮，但早期用户消息字节
   随 todos 改变，同 run 缓存仍在那条消息处反复失配。
6. **只保存 run 开始快照，不处理压缩——毙掉。** 当前代码注释已明确 todos 的原始工具轮会被压缩移走；
   长 run 会失去最新清单及环境上下文。
7. **在模型映射库给 Qwen/GLM 加例外——毙掉。** 本机账本显示 Claude、DeepSeek、GLM、Qwen 等均有样本，
   且共同错误在协议选择之前；模型特调会扩大分支而不治源头。
8. **压缩时重新计算 context 并写入 manifest——毙掉。** 它会在不可变 run 输入之外制造第二份动态投影；
   尤其 todo 可能同时存在“run 开始快照、最新成功 step、manifest 刷新值”三种版本，破坏唯一真源。
9. **给每条 `WireMessage` 增加 `_contextSegments`——毙掉。** 分组应保留在专用内部 context 段，发送前再与
   真实 user 合并；不为一处统计把所有普通消息都扩成复合状态。
10. **给全部提示词做永久哈希锁——毙掉。** 本次用业务 diff 与现有 prompt 单测证明文案零修改；永久哈希会让
    今后任何合法提示词维护都产生无意义失败。

复审后主案增加两条硬约束：context 必须随 run 初始 INSERT 持久化，重启回放不能靠重新计算；

- 使用正常启动的 qywork Sidecar 与前端，在侧栏建立一个用户可打开的评测工作区，形状与截图里的

- 工作区建议命名为“内部注记真实评测”，每个模型/轮次使用独立 fixture 子目录，初始文件逐字相同；
  不在同一份已经被前一模型修改过的目录上接着跑。
- 每次评测都从前端创建真实会话、选择模型与思考档位、发送消息，保留 conversationId、runId、
  provider_request 账本和最终工作区结果。会话保留到用户验收，用户能直接点开核对，不只交一张汇总表。

### 7.3 固定真实对话脚本

每个模型都使用同一份空 fixture 和同一组原话。提示中**故意不写**“不要重复播报/不要说继续”，
否则无法判断结构修复是否生效。

**用户第 1 轮：**

> 在当前空目录做一个可运行的“子 agent 协作演示”网页。先检查目录并列清单；委派一个子 agent
> 只读审查需求并返回检查清单；父 agent 根据回执创建 `index.html`、`styles.css`、`app.js` 和
> `README.md`。页面要展示父/子 agent 的分工、三张任务卡、运行状态切换和一段执行日志；不用外部依赖。
> 完成后运行本地静态检查，发现问题就修复，最后说明启动方法、验证结果和仍未完成的内容。按现有工具完成，
> 不要停下来向我确认细节。

这句话必须自然触发：一次 todo 建立、至少一次 subagent、多个文件工具轮、一次命令验证和 todo 更新；
若某模型绕过这些步骤直接写结论，该轮记为“任务执行不合格”，不能拿它较少的 provider turn 当成“不重复”。

每轮同步生成一条 **todo 时间线**：按 step seq 列出每次成功 `write_todos` 的完整清单，标出当时唯一的
`in_progress`、随后实际发生的 tool/file/subagent 行为、下一版清单的状态变化。失败的 `write_todos` 单列，
不得覆盖最后成功版本。清单允许因发现新工作而完整修订，但不能悄悄漏掉未完成项后宣告 completed。

**用户第 2 轮（只在“调整方向”样本中，于父 agent 至少完成两次工具调用后发送）：**

> 补充一项：README 里增加“父 agent 与子 agent 如何分工”这一节，并在页面日志中体现审查回执被父 agent 采用。

它是一条真正的 user step，模型在它之后简短确认一次不判为错误；但后续没有新用户消息时，不能每个工具轮
继续重复确认这条补充要求。对照样本不发送第 2 轮，用来区分跟进注入与普通工具循环。

**用户第 3 轮（父 run 结束后发送）：**

> 请只根据刚才真实执行记录，概括实际创建了什么、哪些检查通过、还有没有未完成项。

前端收尾条仍不得额外显示“已完成”；模型正文与 UI 状态是两件事。

修后会话按风险分层，不为凑数量机械复制：

1. **Qwen/GLM/DeepSeek 普通对照**：只发第 1、3 轮；
2. **五组模型跟进注入**：第 1 轮运行中发送第 2 轮，再发第 3 轮；
3. **条件式稳定性复跑**：任一模型出现结构性重复、todo 断驱或无法归因的缓存异常时，才逐字重复对应样本，
   使用独立 fixture 和新会话区分随机性与确定性回归。

长上下文、压缩和重启另按批 5.4 在重点兼容模型上扩展，不拿它替代上述基础会话。

### 7.4 重复开头的判定与报告

评测单位是一次 provider turn 产生的父会话 assistant 文本/思考，不是最终把多个 step 折叠后的整页截图。
先用审计脚本标记，再逐条人工复核；审计脚本只读账本，**绝不进入生产输出链路**。

初筛词组包括但不限于：

- `收到提示`、`收到系统提示`、`收到，继续`、`确认清楚了`、`好的，继续`；
- `继续第 N 步`、`继续待办 N`、`接着完成第 N 项`；
- 没有新写入却重复的 `记忆已写入`、`待办已更新`、`我将继续执行`；
- thinking 中的 `system reminder`、`系统提示要求我继续`、`我收到了系统提示`。

不能只按关键词一刀切。每条标记必须归入三类之一：

1. **结构性重复**：没有新 user、todo 状态也没变化，只因又收到内部注记而复述；这是失败。
2. **真实进度更新**：刚完成文件/测试/todo 更新，正文提供新信息；这是允许的。
3. **用户主动询问/补充后的单次回应**：第 2、3 轮后的合理回答；这是允许的。

修后验收目标：

- 三协议最终请求体中的额外 reminder user/system 为 0；
- 可见 thinking 的模型中，因内部尾注产生的 `system reminder/系统提示` 自述为 0；未回传 thinking 的记 N/A；
- 每个计划内合格会话中，结构性重复开头为 0；任何一条非 0 都附原文、前后 tool_result 和请求序号，
  不能用“总体比例下降”判通过；
- 第 3 轮总结、真正变化时的进度说明和最终正文完整存在，证明没有用过滤器换取 0 次重复。
- todo 驱动另外判一条独立结论：每次没有工具的 `end_turn` 若仍有未完成项，下一请求必须留在同一 run；
  每次清单真实变化不能被当作 no_progress；最后 run 只有在最新成功清单全部 completed 时才可 completed。

### 7.5 缓存命中验收

每次 provider 请求记录以下原字段：`turnIndex`、`retryIndex`、`inputTokens`、`cachedTokens`、
`cacheWriteTokens`、`source`、`payloadHash`、`cacheRouteFingerprint`、`sentCategories`、
`finishReason`。报告不得只放一个会话累计百分比。

两层证据分开判：

1. **本地确定性证据**：脱敏后的实际请求消息序列与公共前缀长度。同 run 的请求 N 必须是 N+1 的前缀，
   跨 run 时上一 run 末请求必须完整落在下一 run 首请求前缀内；精确重试 payload hash 必须相同。
2. **provider 黑盒证据**：原始 cached/write 数。`null`/未回报显示 N/A，明确 0 才是 0，不向前找上一轮，
   也不以本地估算冒充 provider 命中。

与既有结果的比较规则：

- 存量会话升级后的第一次请求允许一次冷启动；它不进入稳态统计。从新线形第二次请求开始比较。

最终每个模型给一张逐请求表，再给一行结论：`本地前缀通过/失败`、`provider 命中稳定/抖动/N/A`、
