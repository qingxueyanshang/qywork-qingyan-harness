# 子 agent 与外部 CLI

模型可以把一件事交出去：交给**临时子 agent**、交给**配置好的角色**，或者交给
**本机装着的外部 agent CLI**。派一件用 `subagent`，派一张有先后依赖的图用 `workflow`。

**这里是两件事，不是一件事的两种形态。**

- **角色（子 agent）**：跑在本进程的 agent 循环上，配的是「它是谁、能用什么、受什么约束」。
  它没有「跑在哪」这个字段——它只跑在这里。
- **外部 CLI**：本机装着的别家 agent 程序。它由**识别**得到，不由用户填命令与参数。

配置只有角色那一半，放在工作区的 `.qy/team.json`。**没有这个文件也能派活**——
不指定目标就临时起一个子 agent。

---

## 临时子 agent

不指定目标时用的那一种：当前会话的模型、全套工具、任务结束即销毁。

```
subagent(task: "读一下 notes 目录，报回有几个文件")
```

要并行铺开去查、去读、去验证时用它——为了几件小事先定义几个角色，没人会这么用。
它与角色的唯一区别是「有没有事先写下来的提示词与工具面」，执行路径完全相同。

---

## 角色

```json
{
  "roles": [
    {
      "id": "analyst",
      "name": "分析",
      "description": "读代码、定位问题",
      "systemPrompt": "你只分析不改代码。给出结论和依据，不要动文件。",
      "allowedTools": ["read_file", "grep", "glob", "list_dir"]
    }
  ],
  "rules": { "shared": "禁止修改 CI 配置", "maxConcurrent": 3 }
}
```

| 字段 | 说明 |
|---|---|
| `id` | 派活时用它引用（`subagent(agent: "analyst")`、图节点的 `agent`） |
| `name` / `description` | 前者显示，后者说明该把什么交给它——调度者据此选人 |
| `systemPrompt` | 追加到该角色系统提示词的约束 |
| `provider` / `model` / `effort` | 用哪个接口、哪个模型、什么强度。**不填就跟着当前会话** |
| `allowedTools` | 只给这些工具。**空数组 = 一个都不给**（纯分析角色），不填 = 全部 |
| `maxSteps` | 该角色单次任务的步数上限 |

`allowedTools` 的空数组和不填是两回事，不要合并——合并会让「只让它分析、不给任何工具」
静默变成「什么都能干」，而且看不出来。

`provider` 指的是「用哪家的 key、按谁计价」。**指了一个不存在的接口会当场失败**：
悄悄回落到当前接口会让「用便宜模型跑审查」这类配置静默失效，而账单在另一边。

角色也可以由模型自己写（`define_subagent`）——它只动 `roles`，`rules` 是你的，它碰不到。

## 外部 CLI

不配置，只识别：认得的几家写在 `packages/team/src/cli-detect.ts` 的 `KNOWN` 表里
（Anthropic claude、OpenAI codex、Google gemini、阿里云 qwen、xAI grok、月之暗面 kimi）。
每一家探两件事：**装没装**（PATH 上找得到可执行文件）、**接没接入**（环境变量或凭证文件在不在）。

派给它写 `cli:<id>`：

```
subagent(agent: "cli:claude", task: "…")
```

**代价明写**：那张表会过期。某家改了调用参数，这里就调不动它；某家改了凭证存放位置，
就会把已经登录的那条报成「未接入」。两种都表现为界面上少一条或状态不对，
不会表现为跑到一半失败。加新的一家就往 `KNOWN` 里加一条。

外部 CLI 与子 agent 有三处不同：

- 它用**它自己的模型和 key**，`model` 参数对它不成立，填了当场拒；
- 它**没有子会话**——它是本机另一个进程，所以点开它看到的是它写出来的那段流，
  不是一条会话；
- qywork 自己配置里的 key 会按**值**从它的环境里剥掉（它需要它自己的 key 才能干活，
  所以不能按名字一律剥）。

### 回执

派给它的任务尾部会被追加一节输出格式要求：**交付物正文在前，回执作尾节**——
改了哪些文件 · 怎么解决的 · 还剩什么没做。顺序是硬要求：产出取的是它最后那段文字，
回执写在前面会让查询型任务的答案变成一句状态汇报。

**它改了什么不听它自述，由这一侧量**：起进程前后各照一棵快照树再相 diff，
索引和对象都落在一次性的临时 git 目录里，**跟工作区自己是不是仓库无关**。
所以它自己 `git commit` 了照样量得到，工作区在它跑之前就脏也不会记到它头上，
工作区自己的 `.gitignore` 挡住的不算。

清单只列改得最多的前几个，被截掉的由总数说出来。**「一个文件都没改」和
「量不了」是两回事**：前者写 0 个文件，后者整块缺席并说明原因（这台机器上
跑不了 git）——把后者显示成前者是撒谎。

拿到这两样之后要不要复核、要不要回退，是派活那一方自己的判断：文件就在工作区里，
`read_file` 读得到，`git checkout` 回退得了。**没有任何东西会弹出来问人。**

被派出去的 CLI **在工作区内可以直接改文件**，不会再向谁要一次确认——它那一侧的
stdin 是关的，没有人能应答。不这样的代价实测付过（2026-08-24）：claude 的四种写法
全被它自己的权限闸拦下，回来照样报「做完了」，而工作区一个字节没变。

## 图

```
workflow(goal: "…", nodes: [
  { id: "diag", task: "定位问题：{goal}" },
  { id: "fix", agent: "implementer", task: "按下面的分析改", needs: ["diag"] },
  { id: "check", agent: "cli:claude", task: "复核", needs: ["fix"] }
])
```

图**由模型一次性画出来**，不预先写在 `team.json` 里：编排图是这一次任务的，不是项目配置。
执行仍然是确定性的代码——依赖顺序、并发闸都由编排器按图跑，模型不参与「下一步派谁」。

- 节点不写 `agent` = 临时子 agent；写角色 id = 那个角色；写 `cli:<id>` = 外部 CLI。三种可以混。
- `{goal}` 替换成用户的原始诉求。
- `{input}` 决定上游产出**插在哪里**。不写 `{input}` 时上游产出追加在任务末尾的
  「## 上游产出」小节下——声明了 `needs` 却拿不到产出，表现是下游回「没有上一步的上下文，
  无法复核」，而配置看起来完全正确。真的只想要执行顺序，写 `passInput: false`。
- 不写依赖的节点**并行**跑，受 `rules.maxConcurrent`（默认 3）限制。
- 上游失败时下游**跳过**，不拿着坏输入继续。
- 成环、悬空依赖、引用不存在的角色在加载期就拒绝，不留到运行时变成「一直没有可启动节点」。

图在会话里画成一张卡：节点按依赖分层，同层并排，层间连线指向下游；走向一个正在跑的
节点的那几段线在流动。点节点——子 agent 打开它那条子会话，外部 CLI 打开它写出来的那段流。

## 上下文与产出

每个子 agent 是一条**独立会话**。成员之间、成员与父会话之间的上下文都不共享：
一个「审查者」如果看得见「实现者」的完整思考过程，它就不再是独立视角了，
而独立视角正是多角色的全部意义。要传递的东西由编排器显式拼进 prompt。

回到父会话的只有**最终那段文本**。子会话本身完整留在账本里（点节点就能看），
但它不占父会话的上下文。

**做没做完看的是那一轮的终态**，不是「有没有文字」：被步数上限掐断、原地打转、
被中断的子 agent 一律算没做成，原因原样带回父会话——模型据此换做法，
而不是拿着半截产出往下走。

---

## 没有任何「问用户」的环节

派活、跑图、装插件都不弹授权。工具授权由运行时就地裁决（`auto` / `full` 两档），
被拒的调用以失败的工具卡出现在会话流里。

---

## 用量

**每条子会话的用量记在它自己那条会话上**，父会话的读数条不含子会话。
要看某个节点花了多少，点开那个节点。

不做「这张图一共花了多少」的汇总：外部 CLI 的钱花在别家账上，这里拿不到，
合计必然缺项——而一个会撒谎的数比没有更坏。
