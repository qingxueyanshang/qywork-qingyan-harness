# 子 agent 与外部 CLI

模型可以把一件事交出去：交给**临时子 agent**、交给**配置好的角色**，或者交给
**本机装着的外部 agent CLI**。派一件用 `subagent`，派一张有先后依赖的图用 `workflow`。

**这里是两件事，不是一件事的两种形态。**

- **角色（子 agent）**：跑在本进程的 agent 循环上，配的是「它是谁、能用什么、受什么约束」。
  它没有「跑在哪」这个字段——它只跑在这里。
- **外部 CLI**：本机装着的别家 agent 程序。它由**识别**得到，不由用户填命令与参数。

配置只有角色那一半，放在工作区的 `.qy/team.json`。**没有这个文件也能派活**——
不指定目标就临时起一个子 agent。

---

## 临时子 agent

不指定目标时用的那一种：当前会话的模型、全套工具、任务结束即销毁。

```
subagent(task: "读一下 notes 目录，报回有几个文件")
```

要并行铺开去查、去读、去验证时用它——为了几件小事先定义几个角色，没人会这么用。
它与角色的唯一区别是「有没有事先写下来的提示词与工具面」，执行路径完全相同。

**`subagent` 是一次性的：产出回来就结束，没有验收关口，也没有续接入口。** 要验收、
可能返工，或长到中途可能被打断还得接着做的任务，改用 `workflow`——哪怕图里只有一个
agent 节点加一个检查点。两个工具的选择只看这一条，与派给谁无关：角色、临时子 agent、
外部 CLI 三种目标两个工具都能派。

## 角色

```json
{
  "roles": [
    {
      "id": "analyst",
      "name": "分析",
      "description": "读代码、定位问题",
      "systemPrompt": "你只分析不改代码。给出结论和依据，不要动文件。",
      "allowedTools": ["read_file", "grep", "glob", "list_dir"]
    }
  ],
  "rules": { "shared": "禁止修改 CI 配置" }
}
```

| 字段 | 说明 |
|---|---|
| `id` | 派活时用它引用（`subagent(agent: "analyst")`、图节点的 `agent`） |
| `name` / `description` | 前者显示，后者说明该把什么交给它——调度者据此选人 |
| `systemPrompt` | 追加到该角色系统提示词的约束 |
| `provider` / `model` / `effort` | 用哪个接口、哪个模型、什么强度。**不填就跟着当前会话** |
| `allowedTools` | 只给这些工具。**空数组 = 一个都不给**（纯分析角色），不填 = 全部 |

`allowedTools` 的空数组和不填是两回事，不要合并——合并会让「只让它分析、不给任何工具」
静默变成「什么都能干」，而且看不出来。

`provider` 指的是「用哪家的 key、按谁计价」。**指了一个不存在的接口会当场失败**：
静默回落到当前接口会让「用便宜模型跑审查」这类配置失效，而账单记在另一边。

角色也可以由模型自己写（`define_subagent`）——它只动 `roles`，`rules` 是你的，它碰不到。
**只有要长期复用的人设才值得建角色**：一次性任务把人设直接写进 `task`，
临时节点同样能指定模型——在图节点上写 `provider` 与 `model` 两列即可，不必先建一个角色。

## 外部 CLI

不配置，只识别：认得的几家写在 `packages/team/src/cli-detect.ts` 的 `KNOWN` 表里
（Anthropic claude、OpenAI codex、Google gemini、阿里云 qwen、xAI grok、月之暗面 kimi）。
每一家探两件事：**装没装**（PATH 上找得到可执行文件）、**接没接入**（环境变量或凭证文件在不在）。

派给它写 `cli:<id>`：

```
subagent(agent: "cli:claude", task: "…")
```

**代价明写**：那张表会过期。某家改了调用参数，这里就调不动它；某家改了凭证存放位置，
就会把已经登录的那条报成「未接入」。两种都表现为界面上少一条或状态不对，
不会表现为跑到一半失败。加新的一家就往 `KNOWN` 里加一条。

外部 CLI 与子 agent 有三处不同：

- 它用**它自己的模型和 key**，`model` 参数对它不成立，填了当场拒；
- 它**没有子会话**——它是本机另一个进程，所以点开它看到的是它写出来的那段流，
  不是一条会话；
- qywork 自己配置里的 key 会按**值**从它的环境里剥掉（它需要它自己的 key 才能执行，
  所以不能按名字一律剥）。

### 回执与接着问

派给它的任务尾部会被追加一节输出格式要求：**交付物正文在前，回执作尾节**——
变更文件 · 实现方式 · 未完成项。顺序是硬要求：产出取的是它最后那段文字，
回执写在前面会让查询型任务的答案变成一句状态汇报。

**回执说不清楚就接着问它**，不要重新派一遍——重派会让它把活再做一次。结果里那个
`session` 就是入口：

```
subagent(agent: "cli:claude", task: "你刚才改了哪些文件？只列文件名", resume: "<上一次的 session>")
```

它那条会话还在，记得上一轮干了什么。实测（2026-08-25）追问「你刚才具体改了哪些文件」，
claude 与 codex 都凭记忆答得出来，没有重新去读文件。

**接不上的那几家当场拒绝**：认得出会话 id 的是 claude、codex、grok（表里的 `sessionField`
与 `resumeArgs`），其余几家填了 `resume` 会被回一句「只能重新派一次」——
照跑一遍会起一条全新会话，而模型会按记得上一轮行事。

kimi 那条是**能做而没做**：它有 `--output-format stream-json` 与 `-S/--session <id>`，
但本机这台上它的服务端一直回 500，没能采到「答案与会话 id 埋在哪个字段」，
所以表里空着——猜一个填进去的表现是「写着能接着问、跑起来取不到 id」。

图里的 CLI 节点同样带 `session` 回来，所以一张图跑完之后照样能追着某个节点问。

跑成没成看退出码，改了什么看它的回执；要核实就自己 `read_file` / `git diff`，
要驳回就 `git checkout` 或让它重做。**不会有任何确认弹窗。**

被派出去的 CLI **在工作区内可以直接改文件**，不会再向谁要一次确认——它那一侧的
stdin 是关的，没有人能应答。不这样的代价实测付过（2026-08-24）：claude 的四种写法
全被它自己的权限闸拦下，工作区一个字节没变，**而它的退出码仍是 0**，
这一侧照样算它做成了。

## 图

```
workflow(goal: "…", nodes: [
  { id: "diag", task: "定位问题：{goal}" },
  { id: "fix", agent: "implementer", task: "按下面的分析改", needs: ["diag"] },
  { id: "review", kind: "checkpoint", label: "主会话审查", needs: ["fix"] },
  { id: "check", agent: "cli:claude", task: "复核", needs: ["review"] }
])
```

图**由模型一次性画出来**，不预先写在 `team.json` 里：编排图是这一次任务的，不是项目配置。
执行仍然是确定性的代码——依赖顺序、并发闸都由编排器按图跑。到 `checkpoint` 后，本次
调度先把回执返回主会话；主会话核验后，用返回的 `workflowId` 和 `checkpointId` 再次调用
同一个 `workflow`，选择 `approve` 进入下一批，或用 `revise + revisions` 向指定节点的原
conversation/session 续发。图仍是 DAG，返工不会加依赖环。

- 节点不写 `agent` = 临时子 agent；写角色 id = 那个角色；写 `cli:<id>` = 外部 CLI。三种可以混。
- `{goal}` 替换成用户的原始诉求。
- `{input}` 决定上游产出**插在哪里**。不写 `{input}` 时上游产出追加在任务末尾的
  「## 上游产出」小节下——声明了 `needs` 却拿不到产出，表现是下游回「没有上一步的上下文，
  无法复核」，而配置看起来完全正确。真的只想要执行顺序，写 `passInput: false`。
- 不写依赖的节点**并行**跑，受调用时的 `maxConcurrent`（默认 4）限制；已就绪但超过上限的节点会明确显示为等待并发槽位。
- `checkpoint` 是当前主会话的审查屏障，不执行子 agent；下一批必须依赖它。
- **每个 agent 节点后面都必须有检查点**，末尾也不例外，否则整张图在加载期被拒。
  没有裁决者的节点，它的成败无人接受，失败之后也没有回流入口。
- **检查点批准之后仍然可以 `revise`。** 批准不等于解散：核验时看走眼、或者后来发现某个
  节点的产出有问题，仍能对那个检查点发 `revise`，被点名的节点在**它自己那条子会话**里继续做。
  代价明写：`revise` 会撤销该检查点及其下游检查点的批准，并作废下游节点的结果，
  那批节点在后续 `approve` 时重跑。
- 上游失败时下游**跳过**，不拿着坏输入继续。
- 成环、悬空依赖、引用不存在的角色在加载期就拒绝，不留到运行时变成「一直没有可启动节点」。

同一个 workflow 的首次派发、返工和批准在会话里始终投影成一张卡：节点按依赖分层，同层
并排，层间连线指向下游；`checkpoint` 显示为当前会话节点。点 agent 节点——子 agent 打开
它那条子会话，外部 CLI 打开它写出来的那段流；多次返工仍是同一个入口。

## 上下文与产出

每个子 agent 是一条**独立会话**。成员之间、成员与父会话之间的上下文都不共享：
一个「审查者」如果看得见「实现者」的完整思考过程，它就不再是独立视角了，
而独立视角正是多角色的全部意义。要传递的内容由编排器显式拼进 prompt。

回到父会话的只有**最终那段文本**。子会话本身完整留在账本里（点节点就能看），
但它不占父会话的上下文。

**做没做完看的是那一轮的终态**，不是「有没有文字」：原地打转、发生不可恢复错误或
被中断的子 agent 一律算没做成，原因原样带回父会话——模型据此换做法，
而不是拿着半截产出往下走。

被打断的那一次调用没有回执，图上只留下各节点起跑时落库的子会话 id，投影把它们折成
「调用中断」；主会话据此 `revise` 时，已完成节点的产出不在投影里，续发指令里让它
「已完成则复述最终产出，否则接着做」。

---

## 没有任何「问用户」的环节

派活、跑图、装插件都不弹授权。工具授权由运行时就地裁决（`auto` / `full` 两档），
被拒的调用以失败的工具卡出现在会话流里。

---

## 用量

运行页汇总本会话与子会话，不含外部 CLI。

每笔账仍记在花掉它的那条会话上（`usage_ledger` 的 `conversation_id`），
父子关系由 `conversations.parent_conversation_id` 表达，汇总时按这一列把子会话收回来。
运行页的清单里子会话的轮次单列一行，带着派给谁的角色 id，展开仍是那一轮的逐请求账。

外部 CLI 不计：它是本机另一个进程，用它自己的 key，这里拿不到它的用量。
